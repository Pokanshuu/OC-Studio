## 3. 文档纪律

1. **一份文档只有一个职责。** 领域文档写做法；`todo.md` 写未做；`现状问题.md` 写债；`待设计决策清单.md` 写等你拍板的。同一段话不许出现两次。
2. **做完就删。** `todo.md` 与 `现状问题.md` 里没有「已完成」区块 —— 完成了就删行，证据留在 git 与 `CHANGELOG.md`。
3. **计划有终局。** 一份计划里每项都变成「完成」或「被取代」时，整份搬进 `归档/`，并在 `归档/README.md` 记一行结论。
4. **删行要留话。** 提交信息里写清是 `todo.md` / `现状问题.md` 的哪一条，否则下一个人（或你自己）会以为它漏了。
5. **不写承诺。** 没定的格式、版本号、兼容性一律标「待定」，别写成既成事实 —— 猜出来的兼容性最后都要重做。
6. **所有面向用户的文档按微软写作规范写**（`CHANGELOG.md`、GitHub Release 说明、欢迎页与帮助文案）。要点：用「你」、主动语态、现在时；一句一个事实，句子短；版本段固定「新增 / 修复 / 改进 / 已知问题 / 升级说明」五类，没内容不列；版本头单独一行日期；不用反问、口语、感叹号和夸张词；术语统一（笔记库 / 回收站 / 创作时间线 / 模板 / 组件 / 字段表 / 编排），界面元素用反引号，命令行与文件名保持原样。
7. **发版固定三件套**：`CHANGELOG.md` 的版本段、`v<版本号>` 的 tag、GitHub Release 说明。三处的说法必须一致，Release 说明从 CHANGELOG 对应版本段压缩而来，不另起一套叙事。

## 4. 代码侧的对应体检命令

文档说「已完成」的东西，通常有一条命令能证明它没坏（全部在 `package.json` 的 `scripts` 里）：

**提交前跑一条就够：**

```bash
npm run check      # tsc --noEmit + eslint + 全部 audit:*（约 30s）
```

| 关心什么 | 命令 |
|---|---|
| 模板 / 组件契约 | `npm run audit:templates` |
| 四份随库配置的写盘纪律 | `npm run audit:stores` |
| 导出与站点 | `npm run audit:export` · `npm run audit:site` |
| 设计令牌与主题 | `npm run audit:design` · `npm run audit:theme` |
| 助手的能力面 | `npm run audit:capabilities` · `npm run audit:agent` · `npm run audit:library-guide` |
| 全量命令清单 | [`../AGENTS.md`](../AGENTS.md) 的「开发命令」一节 |

只跑某几条：`node scripts/audit-all.mjs vault`（按名字过滤）。
Rust 侧另跑 `cargo test --manifest-path src-tauri/Cargo.toml --lib`（44 项，约 20s，不进 `check`）。
