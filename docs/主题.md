# 主题

> 主题 = **界面外壳的皮肤**，不是换一套 CSS。能换的是皮，不是骨。
> 未实现。这份文档定的是"哪些能换、换到什么程度、在哪儿换"。

---

## 0. 一句话

**机制上分三层（令牌 / 材质 / 结构），作用域上分两级（应用 / 页面）。**

---

## 0.1 作用域分两级（关键）

| 级别 | 换什么 | 存在哪 | 例子 |
|---|---|---|---|
| **应用级** | 外壳：菜单栏 / 侧栏 / 状态栏 / 内容面板 / 背景 | 应用设置（每台机器一份） | 暗色木桌；全屏背景图 |
| **页面级** | 实体页的背景、卡片底、强调色 | **模板挂主题 id**（随库走） | 「不同国家的角色用不同背景」 |

两级可以组合：外壳是深色木桌，页面是一张纸；或者外壳是纸，页面是一张照片。

**为什么必须分开**：外壳是你坐在哪儿写，页面是你在写什么。把两者塞进一个"主题"，就会出现"换了个国家背景，菜单栏也跟着变了"。

---

## 1. 三层

| 层 | 内容 | 开放程度 |
|---|---|---|
| **令牌** | 色值（paper / ink / line / hover / scrim / danger）、强调色 | **全开放**，但导入时校验对比度 |
| **材质** | 表面材质（纯色 / 渐变 / 模糊 / 背景图）、边线有无、密度（紧凑 / 宽松） | **开放**，但提供预设；背景图强制带遮罩 |
| **结构** | 外壳排布：侧栏位置、菜单栏形态、内容区是否卡片化 | **不开放**。只给 2–3 套内置"外壳样式"（纸 / 玻璃 / 极简） |

**结构不开放的理由**：结构一旦自由，每加一个组件就要在所有外壳形态下测一遍；而且它会让"侧栏 / 内容面板 / 浮层"的层级关系失控——现在那套"一块 `bg-paper` + 一条 `border`"的规矩正是靠结构固定才成立的。

### 1.1 官方主题 = 内置的自定义主题

**官方主题不是另一套实现，就是几份 `theme.json` 放在内置目录里。**

| | 官方主题 | 用户主题 |
|---|---|---|
| 数据结构 | `theme.json` | `theme.json`（同一份） |
| 加载路径 | 内置目录 | 导入 / 用户目录 |
| 能改的层 | 令牌 + 材质 | 令牌 + 材质 |
| 能否覆盖结构 | 不能 | 不能 |

一旦官方主题走"硬编码一套、用户主题走另一套"，两边就会开始互相追赶——所以第一天就要同构。**内置主题是你允许的最大自由度的示范**，它自己先守规矩。

### 1.2 令牌必须声明归属（这是"不打架"的制度保证）

每个令牌新增时必须在 `globals.css` 里登记它属于哪一类，否则主题系统无法安全地做作用域：

| 归属 | 令牌 | 谁能改 |
|---|---|---|
| `shell` | 外壳底色、菜单栏 / 侧栏 / 状态栏表面 | 应用级主题 |
| `page` | `--oc-paper` / `paper-alt` / `paper-card` / `ink*` / `line*` / `hover` / `scrim` | 应用级 + 页面级 |
| `both` | 危险色、强调色 | 都行，页面级覆盖应用级 |

**页面级主题只能改 `page`，碰不到 `shell`。** 这就是"换了个国家的背景，菜单栏不会跟着变"的机制保证——靠的是分组，不是靠自觉。

### 1.3 放开节奏

| 阶段 | 给用户什么 | 风险 |
|---|---|---|
| **v1** | 3–5 套官方主题，只换**颜色 + 背景** | 低。机制先跑通，用户先有选择 |
| **v2** | 开放编辑：色板 / 背景图 / 边线有无 / 密度 | 中。要对比度校验与预设兜底 |
| **v3** | 主题包导入导出、社区分享 | 中高。要 scope 校验 + 版本兼容 |
| **不做** | 结构（侧栏位置、菜单栏形态、内容区卡片化） | — |

每一档都是**在上一档的同一份数据结构上放宽字段**，不是换实现。

## 2. 材质层：背景图是重头

| 项 | 定法 |
|---|---|
| 存储 | `.ocstudio/backgrounds/`（随库走，不是应用设置） |
| 处理 | 上屏用压缩版（长边 ≤ 2560、转 WebP），**原图不进界面**——大图直接当 `background-image` 会掉帧 |
| 遮罩 | 背景图上**强制**一层 `--oc-scrim`，强度可调但有下限（可读性优先） |
| 与 Mica | 设了背景图 → 外壳**必须不透明**，Mica 让位（两者只能取一个） |
| 定位 | 居中填充 / 平铺 / 上下固定（内容滚动时背景不动） |
| 移动端 | 允许，但默认关（耗电） |

---

## 3. 组件契约（新增一条硬约束）

每个组件必须能在**任意主题 + 任意背景**下可读：

- 只用令牌，不写死色值（`npm run audit:design` 已经在管）
- **不许假设背景是纯色**：卡片 / 浮层的半透明底（`bg-paper/85` + `backdrop-blur`）在图片背景上要能读，靠 `--oc-scrim` 保底
- 固定底色上的文字继续用 `text-ink-fixed` / `text-paper-fixed`

---

## 4. 强调色是新增项

现在全站以墨色为主。`--oc-accent` 先只在**图表 / 时间线 / 关系图**里开放；界面控件不开放——否则"一屏不该出现第二块深色"和"选中 = 浅底块"两条规矩同时失效。

---

## 5. 导出与主题

**导出必须用同一套主题渲染**，否则所见非所得。

- 图片导出：用当前页面级主题
- 静态站：用应用级主题，但给一个「强制纸色」选项（更保险、更耐看）
- 打印：强制纸色

---

## 6. 主题包

```
theme.json
├─ id / name / author / version / scope: app|page
├─ tokens:   { paper, ink, line, hover, scrim, accent }
├─ material: { surface: solid|gradient|blur|image, lines: on|off, density }
├─ background: { image, mode, scrimStrength }
└─ preview.png
```

导入校验：颜色格式、**对比度阈值**、资源大小、版本、`scope` 与安装位置是否匹配（页面级主题不能装到应用级）。

---

## 7. 前置与风险

**前置**：`globals.css` 的令牌体系（已有）、`settings.tsx`（已有）。**不依赖模板**——应用级主题可以先做，页面级等模板的「挂主题 id」落地。

| 风险 | 说明 |
|---|---|
| **性能** | 背景图 + `backdrop-blur` 在 Windows WebView2 上代价很高。要么限制模糊区域，要么有背景图时关掉 blur |
| **对比度** | 社区主题最常见的翻车点，导入必须算 |
| **Mica** | 与背景图互斥，做成"二选一"，不能叠加 |
| **安全** | 禁止任意 CSS / JS，只能填值；`scope` 不许越权 |
| **导出保真** | 主题一旦参与渲染，导出的图片 / 静态站就必须用同一套，否则用户截图和导出对不上 |

---

## 8. 工程量

比"换几个色值"大得多，**跟时间线同级**：令牌 + 材质 + 背景图管线（压缩 / 缓存 / 遮罩）+ 主题包 + 对比度校验 + 导出保真。

可以拆：**应用级主题（外壳 + 背景）先做，页面级（模板挂主题）跟着模板走**。
